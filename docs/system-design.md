# Collarbell — system design

> Черновик v0.1 · 2026-10-01 · связано: [mvp-spec.md](mvp-spec.md) (что строим), [product-research.md](product-research.md) (зачем)

## 1. Что проектируем

### 1.1. Части системы

- **Клиенты:** Flutter (iOS/Android), React SPA (веб-приложение для владельцев по адресу `/app/` и админка `/admin/`), лендинг (статика). В v1 добавятся публичные страницы по ссылке: памятка для ситтера, подтверждение прививок, QR-профиль на ошейнике.
- **Backend .NET 10:** API и фоновые задачи.
- **Внешние сервисы:** Firebase Auth, FCM (на iOS через APNs), LLM-провайдеры, объектное хранилище, базы товаров. Позже RevenueCat и почта.

### 1.2. Что определяет архитектуру

1. **Напоминания по времени — главный технический риск и главное отличие продукта.** Кормление нужно напомнить с точностью до минуты, без пропусков и дублей, с учётом перехода на летнее время. Напоминания должны пережить рестарт и деплой.
2. **Семья на нескольких устройствах.** Отметку «покормил(а)» другие видят за секунды, и напоминание у них гаснет.
3. **Медленные внешние вызовы.** AI отвечает от секунд до десятков секунд и упирается в лимиты (429). Базы товаров тоже внешние.
4. **Приватные файлы:** фото паспортов, документов, упаковок.
5. **Публичные ссылки без входа** (v1).

| Параметр | MVP 0.1 | v1 (публичный запуск) | Рост |
|---|---|---|---|
| Семьи | 1–5 | до ~10 тыс. | 100 тыс.+ |
| Пуши в сутки | десятки | ~40 тыс. | ~400 тыс., пики 50–100/с в «круглые» часы |
| Задержка напоминания | ≤ 1 мин | ≤ 1 мин | ≤ 1 мин |
| Доступность | как получится | 99,5% | 99,9% |
| Инфраструктура | ~€10–15/мес | ≤ €50/мес | по выручке |
| Эксплуатация | ~0 | ≤ 1 ч в неделю | — |
| Где данные | ЕС | ЕС | ЕС |

Нагрузка по меркам Postgres небольшая. 40 тыс. пушей в сутки — это в среднем 0,5 в секунду, а FCM принимает пачки до 500 устройств за вызов. Поэтому архитектуру выбираем по критериям надёжности, простоты и цены, а не производительности.

## 2. Варианты

### Вариант A. Модульный монолит на одном сервере — рекомендую

```text
 Flutter (iOS/Android)        React SPA              Лендинг (Astro)
        │ HTTPS/JSON               │ HTTPS/JSON              │
        ▼                          ▼                         ▼
 ┌──────────────── Cloudflare: DNS, TLS, защита, статика ─────────────────┐
 └───────┬─────────────────────────────────────────────────┬───────────────┘
         ▼ api.<домен>                                      ▼ app.<домен>, <домен>
 ┌─────────────── VPS Hetzner (ЕС), Docker Compose ───────┐  Cloudflare Pages
 │ Caddy: TLS, reverse proxy                              │  (SPA и лендинг)
 │   ▼                                                    │
 │ App (.NET 10): один образ, роли включаются конфигом    │
 │   ├─ api:    Minimal API, модули                       │
 │   └─ worker: диспетчер напоминаний, Hangfire           │
 │              (AI-импорт, материализация, файлы)        │
 │   ▼                                                    │
 │ PostgreSQL 18: данные, очередь напоминаний, Hangfire   │
 └──────┬────────────────────────┬──────────────┬─────────┘
        ▼                        ▼              ▼
  Cloudflare R2            Firebase:        LLM (Gemini и др.),
  (файлы, бэкапы БД)       Auth, FCM→APNs   Open Pet Food Facts
```

Код один и Docker-образ один, роли процесса (`api`, `worker`) включаются конфигом.
- **В MVP** обе роли работают в одном контейнере.
- **Когда понадобится**, роли разносятся в два контейнера из того же образа без изменений кода. Тогда деплой API не прерывает диспетчер, а тяжёлые задачи не тормозят API.

**Плюсы:**
- дёшево (~€10–15/мес) и просто;
- одна БД даёт транзакционную согласованность: напоминания пересчитываются в той же транзакции, что и изменение данных;
- удобная локальная разработка, нет распределённых проблем.

**Минусы:**
- сервер — единая точка отказа: если VPS лёг, напоминания не уходят;
- масштабирование только вертикальное;
- обновления ОС и бэкапы — на мне.

**Как смягчаем:**
- внешний мониторинг «пульса» диспетчера с алертом;
- после простоя диспетчер досылает пропущенное;
- ночные бэкапы и ежемесячная проверка восстановления;
- переезд на управляемый Postgres без изменения кода.

### Вариант B. Управляемое облако (Azure)

```text
 Клиенты → Cloudflare / Azure Front Door
   → Container Apps: api (автомасштаб)         → PostgreSQL Flexible Server (бэкапы, PITR, HA за доплату)
   → Container Apps: worker или Azure Functions → Blob Storage (файлы)
   → Service Bus (очереди, отложенные сообщения для напоминаний)
   → Firebase (Auth, FCM), LLM
```

**Плюсы:**
- своих серверов нет, API масштабируется автоматически;
- бэкапы с восстановлением на момент времени включены;
- естественная среда для .NET.

**Минусы:**
- дороже: от ~$35–60/мес на старте, с высокой доступностью БД примерно вдвое больше;
- сложнее локальная разработка и отладка, сильная привязка к вендору;
- записи идут в два места (БД и Service Bus), поэтому обязателен outbox.

**Отложенные напоминания:** хватает Service Bus уровня Basic: отложенные сообщения, $0,05 за млн операций, их можно отменить. Аналоги у других облаков:
- AWS EventBridge Scheduler: разовые расписания, 14 млн вызовов в месяц бесплатно, цели — только сервисы AWS;
- Google Cloud Tasks: до 30 дней вперёд, умеет вызывать любой HTTPS-адрес, в том числе наш VPS.

**Когда выбирать:** от ~10 тыс. активных семей или если нужен ноль администрирования с первого дня.

### Вариант C. Supabase как основной бэкенд + .NET для сложной логики

```text
 Клиенты ──(SDK Supabase: CRUD по RLS, Realtime, Storage, Auth)──▶ Supabase (Postgres)
     └──(HTTPS)──▶ .NET: AI-импорт, напоминания, прогнозы ─────────▶ тот же Postgres
```

**Плюсы:** CRUD делается быстрее всего; синхронизация в реальном времени есть из коробки, отметка «покормил» мгновенно видна всем; Auth и хранилище включены.

**Минусы:**
- логика размазана между RLS-политиками, edge-функциями и .NET;
- безопасность держится на RLS: ошибка в политике означает утечку;
- сложнее тестировать, привязка к Supabase;
- бесплатный тариф засыпает через неделю простоя, Pro стоит $25/мес;
- .NET перестаёт быть ядром.

**Не рекомендую** для этого проекта.

### Рассмотрены и отброшены

- **Микросервисы** (отдельные сервисы уведомлений, AI и файлов плюс брокер сообщений): эксплуатация в разы сложнее, а на таком масштабе выгоды нет.
- **Только локальные уведомления на телефоне:** ломается семейный сценарий. Плюс лимит iOS в 64 запланированных уведомления и запрет точных будильников в Google Play.
- **Firebase (Firestore + Cloud Functions) как основной бэкенд:** документная модель плохо ложится на связи «семья → питомцы → планы → записи», и снова нет .NET.

### Сравнение

| Критерий | A. Монолит на VPS | B. Azure | C. Supabase + .NET |
|---|---|---|---|
| Стоимость на старте | ~€10–15/мес | ~$35–60/мес | $0 (засыпает) или $25+ |
| Скорость разработки MVP | высокая | средняя | самая высокая для CRUD |
| Администрирование | ОС, бэкапы, обновления, ~1 ч/мес | почти нет | почти нет |
| Надёжность напоминаний | высокая при мониторинге; единая точка отказа — сервер | высокая | зависит от .NET-части |
| Синхронизация устройств | добавляется (SSE/SignalR) | добавляется | из коробки |
| Локальная разработка | отличная | средняя | средняя |
| Привязка к вендору | минимальная | высокая | высокая |
| Путь роста | разнести роли → управляемый Postgres → B | уже там | переписывать на .NET |
| Соответствие выбранному стеку | полное | полное | частичное |

**Рекомендация: A.** Переход к B возможен по частям: сначала управляемый Postgres, потом worker на отдельной машине. Файлы и так лежат в R2.

## 3. Вариант A подробно

### 3.1. Модули внутри монолита

```text
App
├─ Identity       пользователи, семьи, приглашения, контекст текущей семьи
├─ Pets           питомцы, вес, шапка паспорта
├─ Care           планы, записи, пресеты
├─ Appointments   визиты
├─ Documents      документы, файлы в R2, обработка изображений
├─ Routines       кормление и лекарства: вхождения, отметки
├─ Supplies       товары, события запаса, прогноз, каталог Product
├─ Ai             подключения, импорт, быстрый ввод, учёт расхода
├─ Notifications  устройства, настройки, очередь напоминаний, диспетчер, FCM
├─ Today          агрегатор главного экрана (только чтение)
└─ Shared         время (NodaTime), ошибки, авторизация, доменные события
```

- **Своя схема в Postgres у каждого модуля** (`care.*`, `routines.*`, …). Чужие таблицы напрямую не читаются, только через публичный интерфейс модуля. Это проверяют архитектурные тесты.
- **Один `DbContext`** с конфигурациями по модулям: так проще транзакции. Отдельный контекст появится, только если модуль уедет в отдельный сервис.
- **Доменные события обрабатываются в той же транзакции.** Например, `CarePlanChanged` пересчитывает напоминания, а `RoutineCompleted` отменяет повторный пуш.
- **Внешние эффекты (пуши, письма, вызовы LLM) — только через таблицы-очереди** (outbox) и фоновые обработчики. Тогда не бывает ситуации «данные сохранились, а пуш потерялся» или наоборот.

### 3.2. Данные

- **PostgreSQL 18.** Идентификаторы UUID v7. Моменты — `timestamptz` в UTC. Локальные даты и время — `date` и `time` + часовой пояс семьи. JSONB — для черновиков AI и произвольных полей товара.
- **Объёмы:**
  - без файлов ~1 МБ на семью в год, 10 тыс. семей — единицы гигабайт;
  - файлы ~0,5–1 МБ на фото после сжатия, 10 тыс. семей — порядка 50–100 ГБ, в R2 это $1–2/мес.
- **Ключевые индексы:**
  - частичный `notifications.scheduled (fire_at) WHERE status = 'Pending'`;
  - уникальный `routine_completions (routine_id, occurrence_date, occurrence_time)`;
  - `household_id` на всех таблицах семьи.
- **Чистка.** Отправленные и пропущенные напоминания старше 30 дней удаляются. При росте — партиционирование по месяцам.

### 3.3. Потоки

**Поток 1. Кормление: напоминание и отметка**

```text
worker (ежедневно и при изменении расписания)
  → материализует вхождения на 48 ч вперёд: notifications.scheduled(Pending, FireAt = 08:00 по поясу семьи → UTC)

диспетчер (каждые 15–30 с)
  BEGIN
  SELECT … WHERE status='Pending' AND fire_at <= now() ORDER BY fire_at LIMIT 500 FOR UPDATE SKIP LOCKED
  для каждой строки:
    кормление уже отмечено?                 → Skipped
    fire_at старше окна догоняния (30 мин)? → Expired (не будим людей устаревшим напоминанием)
    иначе → FCM SendEachForMulticast на все устройства семьи
            collapse-id = routine:{id}:{дата}T{время}, TTL 1 ч → Sent
            ошибка → Failed, Attempts+1, повтор с паузой; недействительный токен → удалить устройство
  COMMIT

Аня нажимает «Покормила» (в приложении или кнопкой в уведомлении, 0.2)
  POST /routines/{id}/completions → INSERT с уникальным ключом → 201
    в той же транзакции: повторное напоминание → Skipped; в очередь — уведомление-замена
  у остальных: тот же collapse-id → уведомление заменяется на «Покормила Аня, 08:02», без звука
  открытые экраны «Сегодня» обновляются (см. 3.4)
  второй нажал одновременно → 409 → «Уже покормила Аня в 08:02»
```

**Поток 2. Прививки и обработки**

```text
сохранение плана или записи → в той же транзакции:
  удалить Pending этого плана; вставить напоминания на NextDueOn − 7 / −1 / 0 дней, 10:00 по поясу семьи
диспетчер в срок: план активен и не выполнен? → пуш всем членам семьи (с v1.0 ещё и письмо)
просрочка: ежедневная задача ставит повтор раз в 3 дня, максимум 5 раз
окно догоняния после простоя — 24 ч
```

**Поток 3. AI-скан**

```text
клиент: сканер документов → сжатие, без EXIF → POST /files
  API: тип по сигнатуре, ≤ 15 МБ, повторное кодирование изображения → R2 (приватный бакет) → fileId
POST /ai-imports → AiImport(Queued) + задача Hangfire → 202 { id }
worker: лимитер (N параллельных вызовов на провайдера) → цепочка моделей → JSON → проверки → Ready
        пуш «Скан готов», если пользователь ушёл с экрана
клиент: GET /ai-imports/{id} раз в 2 с → экран проверки → POST /apply
        → записи + пересчёт напоминаний (поток 2)
```

**Поток 4. Прогноз запасов**

```text
покупка, поправка остатка, изменение расписания кормления
  → пересчёт прогноза товара → BuyBy → одно напоминание (upsert по ключу товара)
ежедневно: пересчёт всех активных товаров — это просто арифметика
```

**Поток 5. Вход и контекст семьи**

```text
клиент: Firebase Auth SDK (Google / Apple / ссылка на email) → ID-токен (JWT на 1 ч, SDK обновляет сам)
API: JwtBearer проверяет подпись (ключи Google кешируются), issuer и audience → uid
  первый запрос пользователя → User + семья по умолчанию (идемпотентно по uid)
  контекст запроса: UserId + HouseholdId; все запросы к данным семьи фильтруются по HouseholdId
GET /me/deletion → что станет с каждой группой: удалится, останется у остальных, перейдёт к участнику; + отпечаток плана
DELETE /me?plan=… (вход не старше 5 минут, auth_time) → одна транзакция: строка человека и его группы FOR UPDATE
  (вступление, загрузка, новый питомец ждут и находят группу удалённой); план не тот, что показан, — 409, ничего не удалено;
  группы, где больше никого (или одни помощники),
  удаляются целиком, файлы — через очередь storage_deletions; в общих группах отметки и записи остаются без имени,
  последнего владельца сменяет участник, вступивший раньше всех; строка users, телефоны, настройки, журнал визора
  → «надгробие» identity.deleted_accounts: токен удалённого аккаунта (живёт до часа) получает 401 account-deleted,
  а не новый пустой аккаунт → удаление входа в Firebase (Admin SDK); не вышло — повтор раз в 10 минут
  → отзыв токенов Sign in with Apple — когда появится вход через Apple
GET /me/export → ZIP потоком: README, account.json, households/N-имя/household.json и files/ (каждый модуль даёт своё)
```

**Поток 6. Публичные ссылки (v1)**

владелец создаёт ссылку: случайный токен 128 бит, срок действия, область видимости (памятка ситтера / прививки)
GET /p/{token}: только чтение заранее заданной проекции, rate limit, без внутренних ID, отзыв в один клик

### 3.4. Как устройства семьи узнают об изменениях

| Вариант | Как работает | Плюсы | Минусы | Когда |
|---|---|---|---|---|
| **S1. Опрос** | Обновление при открытии и фокусе, pull-to-refresh, экран «Сегодня» раз в 30 с. Пуш служит сигналом | Просто, ничего не ломается | Задержка до 30 с на открытом экране | Запасной режим, когда SignalR недоступен |
| **S2. Server-Sent Events** | `GET /events` — односторонний поток событий семьи («изменилось, перечитай»), клиент сам переподключается | Встроено в ASP.NET Core 10 (`TypedResults.ServerSentEvents`). Проще SignalR. Во Flutter — пакет `eventflux` | Браузерный `EventSource` не умеет передавать заголовок `Authorization`: нужен fetch-клиент или короткоживущий токен в запросе. При нескольких экземплярах API нужна общая шина (Postgres LISTEN/NOTIFY или Redis). В фоне на телефоне всё равно работает только пуш | v1, когда веб и телефон открыты одновременно |
| **S3. SignalR** — **выбрано** | Хаб на семью, двусторонний канал | Зрелая технология, официальный клиент для React | Официального клиента для Dart нет. Де-факто стандарт `signalr_netcore` обновляется редко (последний релиз — 09.2025), это риск. При нескольких экземплярах нужен Redis backplane или Azure SignalR | С MVP 0.1 (решение от 2026-10-01) |
| **S4. Офлайн-синхронизация (PowerSync)** | Локальная SQLite на устройстве синхронизируется с Postgres через логическую репликацию. Запись идёт через наш API | Работает без сети, интерфейс мгновенный. Flutter SDK и источник Postgres — GA; JWT Firebase поддерживается; есть пример с .NET-бэкендом | Новый компонент. Нужен `wal_level=logical`. Облако: бесплатно до 50 одновременных клиентов (проект засыпает через неделю простоя), Pro от $49/мес; self-host бесплатный | Если офлайн станет важен. Наши UUID-ключи и запись через API сохраняют эту возможность без переписывания |

**Как устроен поток событий на SignalR** (сделано в M6, `Modules/Live/`)

- **Сервер.** Встроенный ASP.NET Core SignalR, типизированный хаб `/hubs/household` (`Hub<IHouseholdClient>`).
  - При подключении сервер находит пользователя, берёт семью из заголовка `X-Household` (как у обычных запросов) и добавляет соединение в группу `household:{id}`.
  - Членство проверяется до добавления — посторонний не попадает в группу даже на миг — и ещё раз после. Так удаление из семьи, случившееся в эту же секунду, всё равно найдёт соединение.
  - Не член семьи — соединение закрывается с ошибкой и запретом переподключаться.
  - Одному человеку — не больше 10 соединений одновременно. Соединение, оборвавшееся во время проверки, места не занимает.
- **События — короткие сигналы «изменилось, перечитай»** без данных: `Changed { topics, origin }`.
  - Темы: `pets`, `passport`, `care`, `weight`, `feeding`, `visits`, `supplies`, `documents`, `imports`, `household`, `plan`. Вес, записанный ветеринаром, хранится в записи осмотра и приходит как `care`: приложение перечитывает по ней и журнал веса.
  - Данных в событии нет, поэтому из него нельзя узнать больше, чем покажет следующий запрос. Детали клиент перечитывает обычным REST.
  - Незнакомая тема — клиент перечитывает всё.
- **Кто отправляет.**
  - Группы эндпоинтов помечены `.ReportsChanges(тема)`. Общий фильтр `/api/v1` после успешного (2xx) изменения (не GET) отправляет сигнал семье запроса — когда ответ уже ушёл и изменение сохранено. Ошибочный запрос никому ничего не шлёт.
  - Отдельно сигналят: вход по приглашению (сигнал получает семья, в которую вошли), удаление участника, новое имя человека (во все его семьи; одинаковое имя при запуске приложения — не новость), смена тарифа в админке и законченный AI-скан.
  - AI-сканы чипа и упаковки и проверка связи ничего не сохраняют, но тратят AI-фото месяца — они сообщают `plan`.
  - Тест следит, чтобы каждый изменяющий адрес `/api/v1` либо сообщал о себе, либо стоял в списке исключений с причиной.
  - Если отправка не удалась, ничего страшного: клиент перечитает данные при следующем подключении.
- **Своё действие не перечитывается дважды.** Приложение шлёт со всеми запросами `X-Client` — случайный id запуска. Сервер возвращает его как `origin` только на соединения того же человека, остальным — `null`. Телефон, сделавший изменение, его пропускает; чужие id телефонов никто не узнаёт и не может выдать своё изменение за чужое.
- **Удалённый из семьи** сразу выводится из группы. Он получает один сигнал `household`, его следующий запрос получает 403, и приложение переходит в другую семью. Ушедший сам слышит это только на других своих телефонах.
- **Вход.** Тот же Firebase ID-токен, что у запросов, в заголовке `Authorization` WebSocket-запроса: `signalr_netcore` на iOS и Android передаёт заголовки. Токена в адресе нет, поэтому он не попадает в журналы nginx.
- **Вход из браузера** (веб-приложение, M6). WebSocket в браузере заголовков не передаёт, а токен входа в адресе остался бы в журналах на весь час своей жизни. Поэтому веб сначала обычным запросом берёт одноразовый билет (`POST /api/v1/live/tickets`, `Infrastructure/Auth/LiveTickets.cs`), а потом открывает `/hubs/household?access_token=<билет>&household=<id>`. Билет годен один раз и одну минуту, неиспользованных — не больше десяти на человека. Схема входа по билету действует только для `/hubs`. В журнале остаётся уже бесполезный билет.
- **Транспорт — только WebSockets, без запроса negotiate** (`SkipNegotiation`).
  - После открытия соединения приложение вызывает `Ready`. Метод отвечает, когда сервер уже добавил соединение в группу; только после этого приложение считает себя «на связи» и перечитывает экраны.
  - Оба nginx (на хосте и в контейнере `web`) пропускают WebSocket на `/hubs/`. Keep-alive SignalR — 15 с, таймауты прокси — 90 с.
- **Разрывы.** Приложение само переподключается с паузами и каждый раз собирает соединение заново со свежим токеном. SignalR не хранит историю, поэтому после переподключения приложение перечитывает данные семьи.
- **Телефон в фоне.** Через 30 с в фоне соединение закрывается, уведомления в фоне доставляет FCM. При возвращении — подключение и перечитывание. Вернулся раньше (камера, выбор фото, «Поделиться») — соединение то же, ничего не перечитывается.
- **Клиенты:**
  - **Flutter** — `signalr_netcore` за своим интерфейсом `RealtimeClient` (connect, события, состояние соединения). Если пакет подведёт, его заменяют на форк (`signalr_hub`) или SSE, не трогая экраны.
  - Пока соединения нет, открытый экран «Сегодня» перечитывается раз в 30 с (S1).
  - **React** (веб-приложение для владельцев, `web/`): официальный `@microsoft/signalr`, на каждую попытку подключения свежий билет. Админка не подключается.
- **Масштабирование.** На одном экземпляре API backplane не нужен. Когда экземпляров станет больше, понадобится Redis backplane (без negotiate sticky sessions не нужны), этап 4 в 3.9.

### 3.5. Отказы и как их переживаем

| Что сломалось | Последствие | Что делаем |
|---|---|---|
| VPS недоступен | Напоминания не уходят | Внешний мониторинг «пульса» диспетчера, алерт за 2–5 мин. После рестарта досылаем пропущенное: кормления в пределах 30 мин, прививки в пределах суток. Что старше — Expired |
| Деплой или рестарт | Прерванные задачи | Корректная остановка; диспетчер и задачи идемпотентны; уникальные ключи |
| Ошибка FCM | Пуш не ушёл | До 3 повторов с растущей паузой; недействительные токены удаляются |
| Упали после отправки в FCM, но до отметки Sent | Повторный пуш | Тот же collapse-id: пользователь видит одно уведомление |
| LLM ответил 429 или недоступен | Скан ждёт | Цепочка моделей, отложенный повтор, понятный статус в интерфейсе |
| Потеря БД | Всё | Ночной сжатый и зашифрованный `pg_dump` в R2, плюс снапшоты VPS средствами Hetzner. Восстановление проверяем раз в месяц. Позже — непрерывная архивация WAL с восстановлением на момент времени через pgBackRest ≥ 2.57: он работает с R2, но восстановление из R2 пока медленное. WAL-G — только когда исправят зависание `wal-push` на R2 (issue #2550). У R2 нет S3 Object Lock, есть свои блокировки бакета, и они не должны мешать удалению старых бэкапов |
| Ошибка в проверке доступа (IDOR) | Утечка между семьями | Фильтры по HouseholdId + обязательные интеграционные тесты. Позже RLS в Postgres как второй рубеж |
| Потеряны ключи Data Protection | Сохранённые AI-ключи пользователей не расшифровать | Ключи шифрования в БД + бэкап. В худшем случае пользователь вводит ключ заново |
| Перегрузка | API тормозит | Rate limiting, лимит параллельных AI-задач; дальше — разнести роли (3.9) |

### 3.6. Безопасность

- **Периметр:**
  - TLS через Cloudflare и Caddy, HSTS;
  - Postgres не открыт наружу, SSH только по ключу, firewall Hetzner;
  - автоматические обновления безопасности ОС.
- **Секреты:** `.env` на сервере с правами 600 или SOPS-шифрование в репозитории. В git только шаблон.
- **Лимиты запросов** (встроенные в ASP.NET Core): вход, приглашения, публичные ссылки, AI.
- **Файлы:**
  - при загрузке: проверка типа по сигнатуре, лимит размера, повторное кодирование изображений на сервере (EXIF удаляется ещё раз);
  - хранение: приватный бакет, ссылки на скачивание живут 5–15 минут.
- **Цепочка поставок:** Dependabot, сканирование образов (Trivy) в CI.
- **Бэкапы** шифруются перед загрузкой в R2.

### 3.7. Наблюдаемость

- **Логи:** Serilog → stdout контейнера. В MVP хватает `docker logs` и Sentry.
  - С v1 — OpenTelemetry → Grafana Cloud Free. Принимает OTLP напрямую: 50 ГБ логов и трейсов, хранение 14 дней.
- **Ошибки: Sentry** — одна система для .NET, Flutter и React.
  - Бесплатный тариф Developer: 1 пользователь, 5 тыс. ошибок в месяц.
  - Регион ЕС (Франкфурт) выбирается при создании организации, поменять его потом нельзя.
- **Метрики, за которыми следим:**
  - задержка диспетчера: now − fire_at самого старого Pending;
  - доля неудачных пушей;
  - время и ошибки AI-импорта;
  - ответы 5xx;
  - свободное место на диске;
  - возраст последнего бэкапа.
- **«Пульс»:** диспетчер раз в минуту пингует Healthchecks.io (бесплатно до 20 проверок). Если пингов нет 5 минут — алерт в Telegram или на почту. Туда же пингует ночной бэкап.
- **Продуктовая аналитика** (с v1): PostHog EU — бесплатно 1 млн событий в месяц, хранение во Франкфурте, есть DPA.
- **Локально: Aspire 13** (AppHost).
  - Одной командой поднимает Postgres, S3-хранилище и API. Даёт дашборд с логами, трейсами и метриками.
  - **MinIO больше не поддерживается** (репозиторий заархивирован), поэтому локальное S3 — SeaweedFS (для Aspire есть интеграция) или отдельный dev-бакет в R2.
  - Генерация docker-compose из Aspire стабильна с версии 13.2, но `aspire deploy` ещё в превью. Поэтому прод-compose держим свой и проверяем его глазами.

### 3.8. Развёртывание

```text
git push → GitHub Actions
  ├─ backend: build → тесты (Testcontainers) → Docker-образ → GHCR
  ├─ контракт: openapi.json актуален, клиенты перегенерированы
  ├─ web, landing: build → Cloudflare Pages
  └─ deploy: SSH на VPS → бандл миграций EF → docker compose pull && up -d
мобильные сборки: локально или в CI → TestFlight / Google Play internal testing
```

- **Миграции** — только обратно совместимые (сначала добавляем, потом удаляем старое), чтобы откат образа был безопасен.
- **Окружения:** local и prod. Staging позже, как второй compose-проект на том же VPS.
- **Инструмент деплоя:**

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| **D1. Compose + скрипт** — **выбрано** | GitHub Actions по SSH: `docker compose pull && up -d` | Проще некуда, всё видно | При рестарте API несколько секунд простоя, клиенты SignalR переподключаются. Для MVP это не важно: напоминания досылаются |
| **D2. Kamal 2** — когда понадобится | CLI, деплой без простоя через kamal-proxy (проверка `GET /up`), любой образ, MIT | Нулевой простой, откаты одной командой | Postgres как «accessory» обновляется вручную, бэкапы на мне. При деплое клиенты SignalR переподключаются |
| **D3. Coolify / Dokploy** | Панель PaaS на своём сервере | Удобный интерфейс, деплой из git | В 2025–2026 у обоих десятки уязвимостей, включая критические RCE. Если всё же использовать — только за VPN (Tailscale) и с быстрыми обновлениями. **Не рекомендую** |

### 3.9. Путь роста

| Этап | Признак | Что меняем |
|---|---|---|
| 1 | MVP — ~1 тыс. семей | Всё как выше, одна машина |
| 2 | Фоновые задачи тормозят API или нужен деплой без пауз | Роли разносятся: api ×2 + worker ×1 из одного образа, балансировка в Caddy |
| 3 | БД занимает больше половины ресурсов или нужны PITR и HA | Управляемый Postgres или отдельный сервер с репликой; архивация WAL |
| 4 | Десятки тысяч семей, несколько экземпляров API | Redis (HybridCache + общая шина для SSE/SignalR); загрузка файлов напрямую в R2 по подписанным ссылкам; партиционирование очереди напоминаний |
| 5 | 100 тыс.+ семей, жёсткие требования к доступности | Вариант B или выделенный сервис уведомлений |
